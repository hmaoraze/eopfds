## 0. 角色与产出目标

你是腾讯云 EdgeOne Makers 平台的服务端工程师。你的任务是在该平台上交付一个「微信对话机器人服务端」，包含：可运行的云函数源码、接口与数据结构设计、记忆存储方案、配置项说明，以及可独立执行的验收测试。

你熟悉以下四个技术事实，并默认它们是本任务的技术边界，不需要重新论证：

1. Makers Functions 的入口签名是 `export default function onRequest(context)`，环境变量只能从 `context.env` 读取。
2. Blob 分布式对象存储通过 `@edgeone/pages-blob` 的 `getStore` 访问，不是边缘函数专属的全局 KV 变量。
3. DeepSeek `/chat/completions` 是无状态接口，服务端必须在每次请求中自行拼接完整对话历史。
4. wechatbot.dev 的 iLink 协议用长轮询 `getupdates` 拉取消息，发送回复必须回传入站消息的 `context_token`。

产出必须满足：逻辑完整（无未定义行为、无「视情况而定」的占位）、约束明确（每条约束可被代码或测试判定真假）、交付物清单可独立验证（第三方只读文件即可判断是否完成）。

## 1. 硬约束（优先级最高，任何设计决策不得违反）

编号规则：违反任一条即为交付失败，不接受「权衡后妥协」的解释。

- **A1 运行时**：入口必须是 `export default function onRequest(context)`。环境变量读取路径只能是 `context.env.<KEY>`。禁止使用边缘函数专属的全局 KV 变量（KV 不在 `context.env` 上，本需求整体禁用 KV）。
- **A2 存储**：唯一持久化介质是 Blob 分布式对象存储，通过 `@edgeone/pages-blob` 的 `getStore` 获取，版本 `>= 0.0.14`。
- **A3 强一致**：创建 Store 时必须显式写入 `consistency: "strong"`，使该 Store 上所有 `get` / `list` 默认跳过边缘缓存、直读主存储。理由必须写进代码注释：会话续接与记忆写入属于「写后立即读」路径，默认的最终一致性会让上一轮刚写入的数据在下一轮读不到。
- **A4 无托管数据库**：不得引入任何关系型 / 文档型数据库。Blob 的 key 命名方案即 schema，key 设计必须自解释、可前缀列举。
- **A5 无状态上游**：调用 DeepSeek 时必须传入完整的 messages（system 前缀 + 历史 + 本轮用户输入）。不得依赖任何「上游记住了上一轮」的假设，不得使用 `previous_response_id` 一类隐式会话机制。
- **A6 协议兼容**：接收侧实现 iLink `getupdates` 长轮询；发送侧必须携带入站消息中的 `context_token` 原值回传，缺失该字段的回复一律不发（宁可不回，也不能发到错误窗口）。
- **A7 并发形态**：Blob 无原生条件写、无事务，单 JSON 文档的 read-modify-write 在并发下会互相覆盖。因此：
  - 任何会被多用户或多轮并发追加的数据，必须「一条记录一文件」，禁止用单个大 JSON 数组承载并发写入。
  - 会话对象是唯一允许的整文档写入形态，前提是单会话写入串行化（见 B1.4）。
  - 记忆写入的幂等第一道防线是 `store.set(key, value, { onlyIfNew: true })`：key 不存在才写入，已存在则视为重复，转入合并分支。
- **A8 秘密不外泄**：DeepSeek API Key、Blob Store 名称之外的凭据、前置提示词全文、管理员验证凭据，只允许存在于服务端环境变量或受保护的 Blob 配置对象中。任何 API 响应体、任何前端源码、任何日志行都不得出现这些值的明文。

## 2. 功能需求

### B1 统一会话接口

- **B1.1 四类操作**：创建、续接、结束、超时管理，各自对应独立的可调用入口，不得把四件事塞进一个 `?action=` 参数里。
- **B1.2 会话对象**：持久化为单文件 `sessions/{userId}/{sessionId}.json`，字段至少包含：`sessionId`、`userId`、`createdAt`、`lastActiveAt`、`status`、`endedAt`、`messages[]`、`turnCount`、`version`。
- **B1.3 超时判定**：`now - lastActiveAt > sessionTimeoutMs` 即判定超时，`sessionTimeoutMs` 来自服务端配置，不得由客户端传入。超时后会话状态置为 `expired`，后续请求返回明确的过期错误码，不静默续期。
- **B1.4 串行化**：同一 `userId + sessionId` 的读改写必须串行（应用层锁或 in-flight 标记，二选一并在文档中说明选择理由）。理由写进注释：会话整体并发低于记忆库，但同一会话的两条并发消息会撕裂上下文。
- **B1.5 创建时绑定**：新会话创建时记录系统提示词指纹（hash 与长度）与注入模式，写入 `systemSnapshot` 字段，供事后审计「这一轮用的是哪版提示词」。

### B2 前置提示词锁定

- **B2.1 每轮注入**：每轮请求都把同一段可配置前置提示词（人设、行为规则、输出格式约束）作为 `system` message 注入 messages 数组，内容来源只有一个（配置项），不得按会话/按用户改写。
- **B2.2 注入位置只允许两种确定形态，实现必须选定其一并在配置中固化**：
  - 形态 1（`dual_system`，默认）：存在记忆摘要时，摘要作为独立 system message 置于数组最前，前置提示词紧随其后作为第二个 system message；无摘要时数组首位即前置提示词。
  - 形态 2（`merged_single_system`）：摘要拼进前置提示词，合并为唯一 system message，前置提示词占据该消息的头部。
  - 配置值不属于这两个枚举时，启动即报错，不得回退到默认值静默运行。
- **B2.3 用户不可越权**：用户输入只进入 `user` role。历史记录中出现 `role: "system"` 的条目必须在拼接前被丢弃（客户端可能伪造），从机制上保证 system 段无法被用户修改、覆盖或截断。
- **B2.4 非空校验**：前置提示词去空白后为空时，服务拒绝服务，返回明确错误码（如 `PROMPT_EMPTY`）与缺失字段名。不允许「先跑起来再说」。

### B3 记忆双通道写入

- **B3.1 通道 A（主动记忆）**：在 DeepSeek 请求的 `tools` 中声明 `save_memory(content, importance, tags)`。响应含 `tool_calls` 时，服务端执行 Blob 写入，并把 `role: "tool"` 的结果消息按 `tool_call_id` 追加回对话历史，再发起后续生成；工具轮次必须有上限（建议 3），达到上限后降级为不带 tools 的终结请求，不得无限循环。
- **B3.2 通道 A 去重**：写入路径用 `content` 的 SHA-256 哈希作为 `memoryId` 初筛，配合 `onlyIfNew` 保证已存在的 key 不被覆盖。
- **B3.3 通道 B（会话终结提炼）**：会话显式结束或超时后，用完整 `messages` 调一次 DeepSeek 做结构化总结，要求输出 JSON 数组，每条含 `content`、`importance`、`tags`，然后走与通道 A 完全相同的治理流水线（不得有第二套写入逻辑）。
- **B3.4 异步执行**：通道 B 通过 `waitUntil` 在响应返回后执行，不阻塞用户回复。同一会话的提炼最多执行一次（用持久化标记位守卫，避免重复扣费与重复写记忆）。
- **B3.5 解析健壮性**：模型输出可能包裹 ```json 代码块或前后带解释文字，JSON 提取必须做括号配平扫描后再 `JSON.parse`，解析失败只记录失败原因、不写入任何记忆，不得抛出到用户请求链路。

### B4 记忆治理

- **B4.1 存储形态**：`memories/{userId}/{memoryId}.json`，一条记忆一文件。禁止单个大 JSON 数组。
- **B4.2 去重两级**：先内容哈希精确匹配，再应用层文本相似度粗筛（给出具体算法与阈值，默认阈值 0.82，可配置）。
- **B4.3 合并与降级**：相近记忆按 `importance` 与 `lastAccessedAt` 合并（取较大重要度、标签并集、刷新访问时间、`mergeCount++`）或降级（新条目明显更弱时吸收进旧条目、不新增文件）。合并不得覆盖已有 `content` 原文。
- **B4.4 权重公式**：`weight = importance × exp(-λ × daysSinceLastAccess)`，`λ` 可配置，检索排序只依据 weight。
- **B4.5 容量与过期**：支持 `memoryMaxItems` 容量上限（超出按 weight 升序淘汰）与 `memoryTtlMs` 过期淘汰。Blob 无 TTL 自动删除能力，淘汰是逻辑上的 `isActive = false`；物理删除由低频定时任务或手动触发完成，定时任务必须存在。
- **B4.6 检索**：按 `isActive`、`expiresAt`、weight 过滤排序取 top-K，K 可配置。

### B5 新会话记忆注入

- **B5.1 召回**：新会话创建时从 `memories/{userId}/` 前缀召回活跃记忆，按 weight 降序取 top-K。
- **B5.2 压缩**：压缩为简要摘要文本，注入位置遵循 B2.2 选定的形态。
- **B5.3 不改变锁定性质**：摘要注入不得改变前置提示词作为 system role 的锁定性质。
- **B5.4 防指令注入**：摘要内容不得包含任何试图覆盖前置提示词的指令性文本。实现上需要三层：摘要块带「非指令性数据」声明头、单条内容做过长度截断与危险短语过滤、摘要条目被显式标注为用户历史数据而非系统规则。
- **B5.5 稳定性**：摘要在同一会话内保持稳定（创建时生成并缓存），不随每轮请求重新召回，避免上下文抖动。

## 3. 安全与配置

- **C1 配置来源**：所有敏感配置存放于服务端环境变量或受保护的 Blob 配置对象（如 `config/app.json`），通过 `context.env` 读取。
- **C2 Key 不混淆**：EdgeOne Makers 的 Models 网关使用 `MAKERS_MODELS_KEY`，直连 DeepSeek 使用自定义的 `DEEPSEEK_API_KEY`，两者不得互相替代、不得混用、不得默认回退。
- **C3 管理面鉴权**：网页前端配置页面必须具备身份验证。验证逻辑不得依赖前端传入的 `isAdmin` 布尔值，必须在服务端独立校验。至少给出一种可落地方案：Bearer Token + HMAC 时间戳签名（含时间窗与常量时间比较），或复用微信 openid 白名单（并说明 openid 单独使用可被伪造的补偿措施）。
- **C4 脱敏状态接口**：验证通过后 `/admin/config/status` 只返回脱敏状态：API Key 形如 `sk-****abcd`；前置提示词显示为「已加载（N 字符）」或哈希摘要，不得含正文；Blob Store 名称可明文展示（非敏感）。任何接口都不得回显 API Key 明文或前置提示词全文。
- **C5 必填项状态**：前端必须明确展示「必须配置」项状态，至少覆盖：DeepSeek API Key、Blob Store 名称、前置提示词非空、`sessionTimeoutMs` 已设置。缺失项以醒目方式标记为「必须配置」，并汇总为 `requiredMissing` 数组返回前端。必填项缺失时，业务接口返回 `503` + `requiredMissing`，不得以空配置降级运行。
- **C6 日志纪律**：日志允许记录 `memoryId`、`sessionId`、`userId` 的哈希或截断值、上游状态码、耗时；禁止记录 API Key、提示词全文、用户消息原文。

## 5. 验收口径（阶段 B 必须逐条自证）

1. 源码中检索不到任何全局 KV 使用；`getStore` 调用处可见 `consistency: "strong"`。
2. 伪造上游返回 `tool_calls`，一轮对话后 Blob 中出现 `memories/{userId}/{hash}.json`，且 `role: "tool"` 消息进入了历史。
3. 同一 content 写入两次，记忆文件数量为 1，`mergeCount` 递增。
4. 把 `sessionTimeoutMs` 调到 1ms，再请求旧会话，返回过期错误码且状态变为 `expired`，同时触发一次提炼（有标记位）。
5. 历史里手工塞入 `role: "system"` 的伪造条目，实际发往上游的 messages 中该条消失，system 段仍为配置值。
6. `SYSTEM_PROMPT` 置空启动，业务接口 503 且 `requiredMissing` 含 `SYSTEM_PROMPT`。
7. 管理面响应体全文搜索不到 API Key 明文与前 8 位之后的提示词内容。
8. 第二条消息发往上游时，messages 长度大于第一条，且前两条恒为 system。
9. 入站消息带 `context_token: "ct-abc"` 时，发送侧 payload 中该字段原样存在；缺失时发送被拒绝。
10. `npm test` 不联网即可跑通全部用例。
